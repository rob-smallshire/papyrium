# b2

b2's printer output, read from its source (commit `e1c9b84a`, March
2026). Paths below are under `src/`.

## The menus

Printer > Parallel printer attaches the printer. Below it, a disabled
item reports "Printer data: N bytes", then Reset printer buffer, Copy
printer buffer (with Copy options), and Save printer buffer.... Reset,
Copy and Save are enabled only when the buffer holds something
(`b2/BeebWindow.cpp`, `DoPrinterMenu` and its command handling).

Whether the printer is attached is not among the saved window settings
(`BeebWindowSettings` in `b2/BeebWindow.h`), so it must be turned on
again after each launch.

## What happens to a byte

b2 emulates the parallel handshake (`beeb/src/BBCMicro_Update.inl`,
under `BBCMicroUpdateFlag_ParallelPrinter`). When the printer is idle
and the operating system pulls CA2 low (the strobe), the byte on User
VIA port A is appended to the printer buffer and the printer goes busy
for 10 update ticks; CA1 pulses low as the busy count reaches 1, which
is the acknowledge. Attaching the printer gives one CA1 pulse so the
operating system sees a printer (`BBCMicro::SetPrinterEnabled`,
`beeb/src/BBCMicro.cpp`). The printer is never busy for longer than
that, so nothing outside the emulator can make the BBC wait.

The buffer (`PrinterBuffer`, `beeb/src/BBCMicro.cpp`) is a byte vector
behind a mutex. It belongs to the emulator thread rather than the
emulated machine, so it survives resets and loaded states
(`b2/BeebThread.cpp`, where the machine is replaced). Nothing reads it
while the emulator runs except the menu's byte count.

Attaching the printer sends nothing: the buffer fills only when the BBC
prints. b2's own test (`beeb/tests/test_beeb.cpp`, `PrinterTest`) types
`*FX6` then `VDU 2:PRINT "PRINTER TEST":VDU 3` and expects
`PRINTER TEST`, LF, CR in the buffer. If printing to the parallel port
still gives nothing, check `*FX5` or, on a Master, `*CONFIGURE PRINT`.

## Getting the bytes out

- **Save printer buffer...** writes the whole buffer, raw and
  unaltered, to a file (offered as `.dat`). This is a faithful capture.
- **Copy printer buffer** puts a text rendering on the clipboard,
  stripping control codes and translating line endings. Not useful to
  Papyrium.
- **Reset printer buffer** empties it, after confirmation.

b2 has an HTTP API (`b2/HTTPMethodsHandler.cpp`), but its methods
(reset, paste, poke, peek, mount, run, launch) do not include the
printer buffer.

There is no live output: the bytes leave b2 only when the user saves
them.

## Collecting the output

**As b2 stands:** print, Save printer buffer..., give the file to
Papyrium as one job, then Reset printer buffer so the next save does
not include this job again. `papyrium print FILE` prints it as a job of
its own, numbered with the others in the job directory; `papyrium send
FILE` gives it to a running `papyrium serve` on its raw TCP port, so it
joins that printer's jobs.

**With a change to b2:** the place where the byte is appended to the
buffer is where it could also be streamed out as it is printed, either
appended to a file (which the file-following transport would collect,
as for BeebEm) or written to a raw TCP connection to port 9100 (which
the existing `raw-tcp` transport already serves, as for Beebium). TCP
would also give b2 real backpressure if the printer were held busy
until the bytes were sent. This would be a change proposed to b2's
author; whether to pursue it is Rob's decision.
